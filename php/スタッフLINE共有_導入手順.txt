最新仕様（ユーザー指定を優先）
・店舗スケジュール：月間カレンダーで表示・追加。店舗予定だけをLINE自動送信する。
・出勤スケジュール：月間カレンダーで表示・編集。LINE共有はしない。
・出勤の共有設定画面は提供せず、古い出勤の設定と送信待ちが残っていてもワーカーが無効化・取消する。
・LINE用の読み取り処理は出勤データを取得しない。
・店舗用の設定URLは /settings/staff-line?stream=store 。出勤は /shift 。

以下は共通の導入・運用手順です。出勤共有に関する過去の記述は上記仕様に置き換わります。

スタッフLINE共有 — 導入・確認手順

対象
GitHub main 12dd68c を基準にした追加機能。PHP 8.1以上 / MySQL / Twig。
LINE配信は店舗スケジュール（schedule_rules）のみ。出勤スケジュールは配信しない。
日ごとの自由メモ、顧客情報、連絡先、休暇理由はLINE共有の取得対象にしない。
店舗予定の非公開は「共有を許可する対象」にチェックを付けないことで指定する。新しい予定は非公開。

公開前に必要な確認
・main への統合は既存のGitHub Actionsからロリポップへの自動デプロイを起動する。
・この変更の本番デプロイ、LINEの実送信（テスト送信を含む）はオーナーの確認を得てから行う。
・作業ブランチ、ローカルテスト、画面見本だけでは本番に反映されない。
・本番DBの接続やデータは今回のローカル調査では参照していない。構成は既存コードと設定見本から確認した。

1. スタッフ用LINE公式アカウント
発注用とは別のMessaging APIチャネルを推奨。チャネルシークレットとアクセストークンをサーバーの
php/config.php の staff_line に設定する。ブラウザーやGitHub、履歴には認証情報を保存しない。

 'staff_line' => [
     'secret' => 'サーバーで設定',
     'token' => 'サーバーで設定',
     'admin_password' => '推測しづらい専用パスワードをサーバーで設定',
     'delivery_enabled' => false,
 ],

既存管理者の暗証番号認証に加え、配信の設定変更・承認・再送・取消には専用パスワードが毎回必要。
既存の「暗証番号を3回間違えると解除」という動作だけではLINE配信操作を許可しない。
現在のシステムは共有ログインのため、承認者の記録は設定されたログイン名。スタッフ個人の識別ではない。

Webhook URL は https://（本番ホスト）/staff-line/webhook 。HTTPSを使用し、Webhookを有効にする。
公式アカウントのグループ参加を許可し、送信対象のスタッフグループに招待する。
署名を検証できたグループ参加・発言イベントから候補IDを取得する。発言本文・発言者は保存しない。
グループ候補は自動で送信先にしない。管理者が対象を照合して選択する。
退出イベントで配信停止。古いWebhook再配信で退出済みグループを有効に戻さない。

2. 初期設定
 /settings/staff-line?stream=store  店舗スケジュール
 /shift  出勤スケジュール（LINE共有なし）

店舗予定の初期状態は配信無効、承認モード、月曜追加なし。出勤の配信機能は提供しない。
対象にチェック → 送り先を選ぶ → 専用パスワードで保存 → 日付を選んで内容を確認する。
自由入力の予定名を共有する場合は、顧客名や個人の事情を含めないように管理者が確認する。
非公開化・削除の通知では、以前の内容を再掲せず「削除・共有終了」と件数を表示する。

3. DB
スタッフ共有の新規テーブルは src/staff_line.mysql.sql から、初回アクセスまたはCLI実行時に作成する。
既存の在庫・顧客テーブルを書き換えない。sql/staff_line.mysql.sql はレビュー・手動適用用の同一内容。
sql/ は既存デプロイの除外対象なので、実行時定義は src/ 内にも配置している。
DDLを実行できる権限が必要。本番導入前にはDBバックアップを取得する。

4. 自動実行
ロリポップのcronで、サーバー上の実際のPHPコマンドとアプリ配置先を確認して、毎分次を起動する。
 PHPコマンド /実際の配置先/php/bin/staff_line_tick.php

Webアクセスによるcron起動は受け付けない。スケジュール判断は常にAsia/Tokyo。
火〜土の当日分は先に配信待ちを作成でき、8:55より前には送らない。
土曜は共有対象の登録がある日曜分を追加し、設定により登録された月曜分も追加する。
登録の有無は、共有を許可した店舗予定だけで判断する。
日月は通常の配信待ちを作成しない。共有済みの今日以降の予定の変更・削除通知は日月も動く。
変更通知はcronによる最長約1分の検出間隔。過去日の変更は通知しない。
未承認は当日末に期限切れ。8:55以降に承認したものは次のcronで送信する。
cronが止まった場合は当日中の再開で追いつく。8:55の実行時刻はサーバーのcron設定と稼働に依存する。

5. 送信開始（オーナー確認後）
最初は承認モードで運用する。配信対象・グループとプレビューを確認し、
サーバー側の delivery_enabled を true にする。確認前は false のままにする。
店舗予定の完全自動モードは管理画面で切り替える。設定保存時は未試行の承認を取り消す。
同日・同じ種類・同じ宛先の通常配信は1回だけ。設定を保存しても受付済み分は再送しない。

6. 失敗時
通信失敗や5xxは指数的に間隔を空けて再送。本文・送り先・X-Line-Retry-Keyは固定する。
200または受付済みIDを伴う409は「LINE受付」と記録。既読や全員への到達を保証する表示ではない。
4xxは自動再送せず設定確認を求める。管理者による再送予約は同じリクエストを使用する。
最初の試行から23時間以上、試行後に元情報や公開設定が変わった場合は自動再送を停止して「要確認」。
結果不明のものを新しい送信番号で強制再送する機能は設けない。
MySQLのGET_LOCKで複数ワーカーと管理操作を直列化し、API受付後の応答消失でも同じ番号で再送する。

7. 履歴と停止
配信・承認・再送・取消の操作履歴と送信試行結果を保存する。
本文と共有内容の控えは90日経過後に削除する。重複防止の識別子、時刻、結果は残す。
cronが停止している間は自動削除も停止する。
停止は店舗予定の共有設定で配信有効を外す。すべての実送信を止めるには delivery_enabled を false にする。
取り消し済みや配信済みのLINEメッセージを、このシステムから遡って回収することはできない。

8. テスト
 php php/tests/staff_line.php
デフォルトは一時SQLiteを使う独立テスト。LINE通信は注入した模擬送信先で検証し、実送信しない。
GitHub Actionsの既存 smoke.php はCI内で同テストをMySQLに対して追加実行する。
MySQLテストはCI=trueかつSTAFF_LINE_TEST_MYSQL=1でのみ実行可能。本番DBでは実行しない。
ほかに既存unit.php、lint_twig.php、PHP文法検査を実行する。
